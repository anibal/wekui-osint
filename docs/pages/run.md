title:: Run
type:: concept

- A **run** is the receipt of one execution of the system's own pipeline over an [[event]]: which stages ran — extract, resolve, verify, render — over what scope, what each produced, and which gates it left open. It records *that the system acted*, never a fact about the world: the facts live in the [[claim]]s and their evidence, and a run is the auditable provenance of how they got there.
- A run is **born running and finalized with a summary**. Two states, deliberately: there is no failed state and no state machine. A crash unwinds the pipeline without unmaking what earlier stages honestly wrote, so a run still marked running long after its start IS the crash signal — a crash artifact, not a live process. An error a stage can catch is carried in the summary instead, and a completed run with errors in its summary is an honest receipt.
- A run carries the [[actor]] that performed it — the executing agent, the same Actor whose prompt extraction uses. Actors are content-addressed and immutable, so a revised prompt mints a *second* agent on the event; the ask must name which one, and the receipt records it.
- A run carries the exact **options** it was asked with — the [[place]], the interval, the executing agent, the per-stage choices — stamped at birth and never revised, so what was asked can always be told apart from what happened.
- A run carries a **summary** of what happened per stage: counts, verdicts, the unresolved leftovers, and the gate queues it surfaced ([[person]]s pending review, proposed [[place]]s, [[claim]]s the support gate flagged). Its counts state their own scope: the extract stage counts the batch it fed, while resolve and verify count an event-wide snapshot of the current claims at run time — on a second run the receipt mixes a batch delta with snapshots, and that is the honest reading.
- A run **never re-decides what a person settled**: a [[claim]] whose place a person set by hand is passed over, and the receipt counts it as *settled* rather than pretending the resolver did the work. A [[curation]] act outranks a later pass, or the pass would silently undo it.
- A run *surfaces* the human gates; it never blocks on them. The gates are statuses on the things themselves, serviced by review later — "not a cop, not a blocker" at the orchestration layer. The one blocking gate is future spend, designed with the acquisition rung.
- A run may record the [[beat]] its render stage produced, as a **receipt of output**. The beat stays derived and re-derivable from the claims — the run's copy is provenance, never the canonical story, and nothing here is a final product.
- A run **refused before it opens leaves no receipt.** Preflight — the worker is ready, the event has an active gazetteer, there are posts in scope — runs before the receipt is born, so a pipeline that never ran is not a record of the system acting.
- The read path a run records has **no agentic decisions**: its stages run in a fixed order over a fixed scope, and an LLM appears only inside two of them. That is why the orchestration is deterministic — see [[decision-2026-07-26-reactor-not-sagents]].
